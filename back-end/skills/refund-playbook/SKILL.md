# 退款处置规程

退款是本系统里唯一直接动钱的流程。这份规程的作用不是让流程变长，而是让
**"退多少、为什么退、政策允不允许"** 这三件事在发起之前就互相印证过一遍——
事后审计要看的正是这三个数是否一致。

## 一、先把事实拿齐

办一张退款工单之前，下面四项必须已经落实。缺任何一项，先问客户或查订单，
不要靠推测往下走。

1. **订单号**——从客户原话里抽，抽不到就用 `lookup_customer` 按邮箱/手机号找到他，
   再在他的订单里挑。绝不自己拼一个看起来合理的单号。
2. **订单状态与实付金额**——`lookup_order` 的结果是唯一依据。已取消、已全额退款、
   未支付这三种状态不能再次退款。
3. **诉求金额**——以客户写明的数字为准。他写"大概一百多"时，把它当成"金额未知"处理：
   风险等级会因此判定为高，这条流程会停在人工审批，那是正确行为。
4. **政策依据**——用 `search_knowledge_base` 检索退换货政策，并**引用到具体文档**。
   政策没覆盖的情形不要自己外推。

## 二、判断该走哪一条

- 只是问"我的退款到哪一步了" → 查询类，直接查退款记录并答复，**不要**发起新的退款。
- 诉求金额 ≤ 政策允许且订单状态正常 → 可以发起退款（资金类，必然挂人工审批）。
- 金额超出政策、订单状态异常、客户提到投诉/法律、情绪极度负面 → **转人工**，
  把已经查到的事实一并交接过去，不要让客户重新讲一遍。

## 三、发起退款

- 一次处置只发一笔：同一张工单里对同一订单退款两次，第二次会被幂等键挡掉，
  这是设计如此，不是故障。
- `reason_code` 用政策里的原词（quality / delay / unwanted 等），不要写散文——
  它是事后统计"哪种原因退得最多"的口径。
- 金额必须与核对过的实付金额或政策上限取较小值。拿不准就填小于预期，
  少退可以再补，多退要追责。

## 四、答复客户

回复里要写清：退了多少、退到哪个渠道、多久到账、依据是哪条政策。
不确定的到账时间不要给具体数字——说"以支付渠道为准"比给一个猜测好。
