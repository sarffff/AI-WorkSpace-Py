notes: 和 agent_plan 的分工不同，那份是"回答问题要几步"，这份是"把这件事办完要几步"，所以措辞里的硬要求是「写操作之前必须先查」和「资金类那步标成人审」——这两条正是治理层真正会拦的东西，计划里不写，人在审批弹窗上看到的就是一个平白出现的退款调用。空计划是合法输出：一步就能办完的工单占多数。这份提示词的输出只用于**注入下一轮上下文与给人看**，不作为执行游标（没有任何可靠信号说明某一步做完了，按轮次推进游标是个看起来精确的假数字，理由同 services/planner.py 里那一段）。JSON 示例里的花括号写成 {{ }}，否则会被当占位符。

你在为一张客服工单规划办理步骤。目标不是回答问题，而是**把这件事办完**：查清需要查的、改需要改的、该退的提出来给人批，最后答复客户。

规则：

- 最多 {max_steps} 步。能一步办完就只写一步，不要凑。
- **任何写操作之前必须有一步是查。** 没查过订单状态和可退余额就发起退款，是错误操作率的主要来源。
- 退款、取消订单这类资金操作，把 tool 写成对应工具名，它会被挂起来等人批准——不要在计划里假设它已经生效。
- 需要人工判断的那一步（比如客户情绪很差、涉及法律措辞）标出来，tool 留空，goal 写清楚为什么要交给人。
- 纯推理的步骤（对比政策、汇总查到的事实、组织给客户的答复）把 tool 留空字符串。
- 只能从下面的可用工具里挑，挑不到的就用空字符串。

工单意图：{intent}
风险等级：{risk}
可用工具：{tools}

工单原文：
{ticket_text}

只输出 JSON 数组，不要任何解释：
[{{"goal": "这一步要得到什么", "tool": "工具名或空字符串"}}]
